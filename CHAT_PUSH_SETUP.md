# Phase 6B: booking chat and Expo push

## Database

Apply `packages/shared/supabase/migrations/06_chat_and_push.sql` once after migrations 01–05. It has not been applied to a hosted Supabase project by this task.

- `booking_messages`: immutable text messages, participant-only SELECT policy, no direct client mutations. `send_booking_message` derives the sender from Auth, locks the booking, validates membership/status and limits messages to 2,000 characters. Reusing the same client message UUID retries safely; a one-second sender rate limit reduces repeated sends.
- `push_devices`: private Expo token registrations, managed through authenticated register/unregister RPCs. Registration refreshes the owner for account changes. Token reads and direct mutations are server-only.
- `push_outbox`: private durable deliveries generated by message inserts and booking status-history inserts. A failed push never rolls back a previously committed booking/message. The worker checks current device ownership and booking membership before sending.

Sending is allowed on assigned `requested`, `accepted` and `in_progress` bookings. Both participants retain read-only history after completion/cancellation. Unassigned job-board viewers cannot access chat. Message timestamps come from PostgreSQL, and message bodies render as plain text.

Migration 06 adds `booking_messages` to the existing `supabase_realtime` publication. Confirm both `bookings` and `booking_messages` are enabled in Supabase Replication. Both UIs subscribe to changes, reload on reconnect and focus/foreground, and poll every 15 seconds. History uses pages of 50 with timestamp/UUID cursors; **Older** loads earlier history and **Latest** returns to current messages.

Web route: `/chat?booking=<uuid>`. Native route: `(app)/chat?booking=<uuid>`. Booking cards provide participant-only links. RLS and the send RPC remain authoritative if someone opens a forged URL.

## Mobile setup

1. Run `pnpm install`. The mobile manifest and lockfile include SDK-compatible `expo-notifications` and `expo-device`; the notifications config plugin is registered in `app.json`.
2. Link the app to your EAS project. Configure `extra.eas.projectId` through EAS, or set `EXPO_PUBLIC_EAS_PROJECT_ID` to that project's UUID in the mobile environment.
3. Configure the Android application ID, iOS bundle ID, FCM v1 and APNs credentials for that project. Build a new development/production client containing the notification native modules. Expo Go is not supported by this integration; use a physical device.
4. Sign in, then select **Enable alerts** on the dashboard. Permission is requested only after this action. Android's `bookings` channel is created first. Foreground/session restoration renews previously enabled registrations without prompting. **Disable alerts** unregisters the device, and normal sign-out revokes registration before signing out.

Push tokens are not the Supabase anon key or EAS project ID. Never expose dispatch/service-role/Expo access-token secrets in mobile environment variables. The project ID itself is public.

Notification taps are restricted to validated booking IDs and the current recipient account, then pass through the normal auth and participant checks. Chat and job status alerts open that booking's conversation. No arbitrary notification-provided URLs are followed. Foreground notifications for another account are suppressed. Lock-screen payloads contain generic alert text, booking/recipient IDs and event kind; they exclude message text, names and service addresses.

Registrations expire from eligibility after 30 days without renewal, with at most ten devices per account. Unexpected session revocation or uninstall can leave a registration until cleanup/expiry; generic notifications avoid leaking chat content during that window. Already accepted OS notifications cannot be recalled on sign-out. A connectivity failure while revoking notifications leaves sign-out pending so the user can retry.

## Server delivery

On the Next.js server, configure:

```dotenv
PUSH_DISPATCH_SECRET=<random-secret-at-least-32-characters>
# Optional; required when Expo enhanced push security is enabled for your project.
EXPO_ACCESS_TOKEN=<server-only-expo-access-token>
```

The worker also uses existing `NEXT_PUBLIC_SUPABASE_URL` and server-only `SUPABASE_SERVICE_ROLE_KEY`. Khalti settings are not needed by the push worker.

Configure a trusted scheduler to POST to `https://YOUR_HOST/api/notifications/dispatch` every minute with header `Authorization: Bearer <PUSH_DISPATCH_SECRET>`. Set the server route timeout to at least 120 seconds. For faster first delivery, additionally configure a Supabase Database Webhook on INSERT into `public.push_outbox` to POST to the same URL with that header. Keep the scheduler: it handles delayed retries and receipt checks. The endpoint ignores webhook body data and claims authoritative queued rows from the database. No scheduler or webhook has been created remotely by this task.

Each call claims at most 20 due deliveries, using leases and `FOR UPDATE SKIP LOCKED` to avoid overlapping workers. It sends with up to four concurrent Expo requests. New messages notify the other participant's registered devices. Status changes notify registered participants other than the actor, including customer-selected professional requests. Unassigned requests do not broadcast to the whole job board.

The worker stores Expo tickets and checks receipts after 15 minutes. `DeviceNotRegistered` removes the invalid registration. Temporary request failures retry with exponential backoff; exhausted jobs become failed after eight claims or 23 hours. Permanent provider errors are recorded for operator review. Inspect `push_outbox.state`, `last_error` and `attempts` with server/admin access, and establish a retention/cleanup policy for processed records. A delivered receipt means delivery to APNs/FCM, not proof the user read it.

Delivery is at-least-once. A network failure after Expo accepts a send but before its ticket is stored can cause duplicate alerts on retry. Receipt retries do not resend the original alert. Device opt-out and membership changes skip queued deliveries where possible.

Before rollout, apply the migration in a test project and exercise customer/professional messaging, outsider rejection, closed bookings, reconnects, duplicate message retries, notification permission denial, account switching, sign-out, job alerts and Expo receipts on physical devices.
